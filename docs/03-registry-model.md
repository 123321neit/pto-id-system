# 03. Модель реестров

## Главный принцип

Реестр — производная проекция, а не главная таблица.

В исполнительной документации реестр выглядит как центральный рабочий инструмент: инженер открывает таблицу, видит список актов, дат, номеров, статусов, сертификатов и комплектов. Поэтому легко ошибочно принять реестр за source of truth.

Архитектурно это неверно. Реестр должен показывать состояние документов и связей, а не хранить их вместо доменной модели.

## Почему реестр не должен быть главным источником

Если сделать реестр главной таблицей, система унаследует ограничения Excel-подхода:

- одна строка пытается описать разные типы документов;
- сложные связи превращаются в текстовые примечания;
- сертификаты и схемы дублируются в ячейках;
- документ может расходиться со строкой реестра;
- изменение акта требует ручного изменения реестра;
- нельзя надежно понять, какие данные актуальны;
- контроль полноты становится набором хрупких правил по колонкам.

Реестр удобен как экран контроля, но беден как доменная модель.

## Что является source of truth

Source of truth для реестра:

- Document;
- typed document data;
- WorkItem;
- MaterialUsage;
- Certificate;
- AsBuiltScheme;
- Package;
- статусы;
- связи между сущностями;
- версии шаблонов и артефактов.

Реестр должен строиться из этих данных.

## Что такое RegistryProjection

RegistryProjection — вычисляемое представление, оптимизированное для просмотра, фильтрации, сортировки, экспорта и контроля.

Она может быть:

- вычисляемой на лету;
- материализованной для скорости;
- экспортируемой в XLSX/PDF/DOCX;
- кэшируемой;
- пересчитываемой после изменений документов.

Но даже материализованная проекция не становится источником истины. Если данные расходятся, побеждает доменная модель.

## Типы реестров

В MVP могут понадобиться разные реестры:

- реестр АОСР;
- реестр актов испытаний;
- реестр сертификатов и паспортов;
- реестр исполнительных схем;
- общий реестр документов ИД;
- реестр состава комплекта;
- реестр замечаний или неполноты, если это будет включено в MVP.

Каждый реестр имеет собственные колонки, но все они строятся из одной модели связей.

## Пример строки реестра АОСР

Строка реестра АОСР может включать:

- номер акта;
- дату акта;
- наименование скрытых работ;
- систему;
- место выполнения;
- период выполнения работ;
- связанные сертификаты;
- связанные исполнительные схемы;
- статус;
- признак готовности DOCX/PDF;
- комплект, куда включен акт.

Но эти значения не должны жить только в строке. Номер и дата берутся из Document, работа — из WorkItem, сертификаты — из связей MaterialUsage -> Certificate, схемы — из AsBuiltScheme, статус — из lifecycle документа.

## Редактирование через реестр

Вопрос редактирования через реестр открыт, но базовый принцип такой: если пользователь меняет значение в реестре, система должна изменять соответствующее structured data поле, а не только текст ячейки.

Например:

- изменение даты акта обновляет Document.date;
- изменение статуса обновляет lifecycle документа;
- добавление сертификата создает или изменяет связь с MaterialUsage;
- изменение названия работы обновляет WorkItem или связь акта с работой.

Если поле является вычисляемым, пользователь не должен редактировать его напрямую без понятной операции.

## Экспорт реестра

Экспорт реестра в XLSX/PDF/DOCX — производный артефакт. Он нужен для передачи, печати и контроля, но после экспорта не должен становиться новой базой данных.

Если пользователь изменил экспортированный XLSX вне системы, это не должно автоматически считаться изменением source of truth. Импорт изменений из внешнего файла требует отдельного архитектурного решения.

## Инварианты

- Реестр не хранит первичные данные вместо документов.
- Реестр может быть материализован, но остается проекцией.
- Любое редактирование через реестр должно маппиться на typed data.
- Экспорт реестра является артефактом.
- Проверка полноты должна опираться на связи доменной модели, а не на визуальное наличие текста в ячейках.

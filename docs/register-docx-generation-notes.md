# DOCX-реестр ИД — engineering notes

Статус: подготовка первого DOCX-реестра. Код генерации DOCX ещё не подключён.

Источник анализа: 4 реальных правильных реестра вентиляции:

- Дэнт-элит — вентиляция/кондиционирование;
- Богданович — вентиляция;
- Бокситовый проезд — монтаж и пусконаладка вентиляции;
- Косулино 2 — устройство систем вентиляции.

Файлы использовались только как эталоны оформления и логики. Их не нужно
парсить как production seed и не нужно показывать в UI.

## Главное решение

Реестр — производный DOCX-артефакт пакета ИД. Он может собираться в двух
областях:

1. **Промежуточный реестр по папке** — для промежуточной ИД за период/этап.
2. **Итоговый реестр по разделу** — по всем папкам выбранного раздела.

Source of truth остаётся structured data. Реестр не должен становиться отдельной
редактируемой таблицей, которая хранит первичные данные вместо актов,
сертификатов, схем, журналов и рабочей документации.

Целевая цепочка:

```text
section/folder structured data -> IdRegisterPrintState -> DOCX template data -> DOCX template -> downloaded .docx
```

Не читать данные напрямую из DOM/UI.

## Структура реестра из реальных образцов

Все 4 образца имеют одну практическую структуру.

### Титульный блок

- название формы: `ПЕРЕЧЕНЬ ДОКУМЕНТАЦИИ...`;
- наименование объекта;
- наименование выполняемых работ.

Для ИДеи:

- объект берётся из настроек раздела/объекта;
- наименование работ для реестра лучше хранить как явное значение раздела или
  scope-пакета, а не вычислять из названия папки.

### Оглавление / список блоков

В образцах перечислены:

1. Перечень исполнителей / подрядных организаций.
2. Комплект рабочих чертежей.
3. Сертификаты, паспорта, декларации и другие документы качества.
4. Исполнительная документация / акты.
5. Исполнительные схемы и съёмки.
6. Журналы.

Раздел `Журналы` оставляем даже если строк нет.

### 1. Исполнители

Таблица содержит:

- лицо, осуществляющее строительство;
- договор/основание выполнения работ;
- виды работ;
- раздел проекта / шифр проекта;
- СРО/лицензия;
- реквизиты;
- руководитель/представитель;
- представитель по строительному контролю.

Текущей demo-модели достаточно только для чернового заполнения. Для production
нужны более структурные поля подрядчика: договор, СРО/лицензия, реквизиты и
ответственные представители.

### 2. Комплект рабочих чертежей

Колонки:

- наименование лица, осуществляющего строительство;
- наименование чертежа/проекта;
- шифр/номер чертежа;
- количество листов.

Текущая модель хранит `projectDocumentation` как текст. Для нормального реестра
нужна структурная сущность рабочей документации раздела: название, шифр,
количество листов, организация.

### 3. Сертификаты, паспорта и документы качества

Колонки:

- наименование документа;
- кем выдан документ, срок действия/дата;
- регистрационный номер документа;
- количество документов, шт.

Сюда попадают не только сертификаты, но и декларации, паспорта качества,
информационные письма и похожие документы. В промежуточный реестр попадают все
документы качества, задействованные актами выбранной папки. В итоговый реестр —
все задействованные документы качества всех папок раздела.

Дедублирование:

- основной ключ — id документа/сертификата из библиотеки;
- fallback — нормализованные `тип + номер + наименование`.

Количество документов/листов пока не покрыто demo-моделью и должно стать
отдельным структурным полем.

### 4. Исполнительная документация / акты

Колонки:

- наименование исполнительного документа;
- регистрационный номер;
- дата оформления;
- примечание.

В образцах здесь есть не только АОСР:

- акты освидетельствования скрытых работ;
- акты индивидуальных испытаний;
- акты технической готовности;
- акты рабочей комиссии;
- акты освидетельствования участков сетей;
- ведомости смонтированного оборудования.

Первый scope кода может покрывать только текущие АОСР, но модель не должна
закрываться на один тип акта.

Акты не дедублируются: каждый акт — отдельная строка.

### 5. Исполнительные схемы и съёмки

Колонки:

- наименование исполнительной схемы/съёмки;
- регистрационный номер;
- дата оформления;
- примечание.

Не создаём отдельный верхнеуровневый раздел продукта `Схемы`. В продуктовой
модели это документы/файлы, связанные с разделом, папкой или актом.

Дедублирование:

- основной ключ — id документа;
- fallback — нормализованные `номер + наименование`.

### 6. Журналы

Колонки:

- наименование документа;
- лицо/организация, ответственная за ведение документа;
- регистрационный номер, дата;
- примечание.

Раздел показывается всегда. Строки берутся из задействованных документов папки
или раздела.

## Scope: папка vs раздел

### Реестр по папке

Берёт:

- все акты в выбранной папке;
- все сертификаты/паспорта/декларации, задействованные актами этой папки;
- все исполнительные схемы/чертежи/журналы/прочие документы, задействованные
  актами этой папки;
- рабочую документацию раздела, если она относится к этому комплекту.

### Реестр по разделу

Берёт то же самое, но по всем папкам выбранного раздела.

Дубли между папками убираются для библиотечных/прикладных документов:

- сертификаты;
- паспорта;
- декларации;
- исполнительные схемы;
- журналы;
- рабочая документация.

Акты остаются отдельными строками.

## Документы объекта vs документы раздела

Текущий UI говорит `Документы объекта`. Для реестра этого мало: часть документов
действительно объектовые, а часть относится к конкретному разделу или папке.

Предлагаемое направление без резкого UI-рефактора:

- сохранить текущую библиотеку как общий документный список;
- добавить/заложить scope документа: `object`, `section`, `folder`, `act`;
- в интерфейсе позже переосмыслить название в сторону `Библиотека документов`
  или `Документы и файлы`, с фильтрами по объекту/разделу/папке;
- не создавать отдельные продуктовые разделы для схем/журналов, а хранить их как
  типы документов внутри библиотеки.

Так мы не ломаем текущую логику, но перестаём смешивать объектовые и
разделовые документы.

## Шаблон DOCX

Решение: первый шаблон реестра с тегами может подготовить Codex на основе 4
реальных образцов, затем пользователь проверяет и правит его вручную в Word.

Причина:

- структура повторяется;
- теги лучше сразу проектировать под renderer;
- внешний вид всё равно требует человеческой проверки: шрифты, отступы, переносы
  строк, повтор заголовков таблиц на страницах.

Шаблон должен быть static asset, как АОСР-шаблон. Реальные реестры остаются
reference fixtures, не production data.

## Что уже покрывает frontend demo

Уже есть:

- папки ИД и порядок актов внутри папки;
- итоговый и промежуточный package scope;
- связь АОСР с сертификатами материалов;
- связь АОСР с документами из текущей библиотеки;
- базовый derived registry screen для списка актов.

Добавлен первый чистый `IdRegisterPrintState` builder:

- строит scope `folder` или `section`;
- сохраняет каждый акт отдельной строкой;
- дедублирует сертификаты по библиотечному документу;
- дедублирует задействованные схемы/журналы по id документа;
- оставляет раздел журналов даже если строк нет;
- пока не генерирует DOCX.

## Чего ещё не хватает для точного реестра

- структурной рабочей документации раздела: организация, название, шифр,
  количество листов;
- количества листов/документов для сертификатов/паспортов/деклараций;
- scope документа: object/section/folder/act;
- отдельной категории/типа для рабочей документации, чтобы не угадывать её по
  тексту;
- структурных данных подрядчика для раздела 1;
- поддерживаемых типов актов кроме АОСР;
- DOCX-шаблона реестра с динамическими таблицами;
- visual QA generated DOCX against the real reference registers.

## Что не делаем в этом scope

- не делаем PDF;
- не делаем ZIP/package builder;
- не делаем backend/API/storage;
- не добавляем Prisma domain models/migrations;
- не делаем AI/OCR;
- не импортируем реальные реестры как данные;
- не читаем данные из DOM/UI.

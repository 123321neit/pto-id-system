# PTO ID System

PTO ID System — web-система автоматизации исполнительной документации для инженеров ПТО.

Проект находится на архитектурной стадии. В репозитории фиксируются принципы, границы MVP, доменная модель, решения ADR и инструкции для дальнейшей работы. Код приложения, зависимости, CI, Docker, frontend/backend scaffold и инфраструктура намеренно не создаются до отдельных архитектурных решений.

## Главный принцип

**Source of truth = structured data.**

DOCX, PDF, реестры, комплекты исполнительной документации и печатные формы являются производными артефактами. Они генерируются из структурированных данных, а не становятся местом, где живет исходная информация проекта.

Это означает:

- данные акта, сертификата, исполнительной схемы и позиции реестра хранятся в типизированной модели;
- документы собираются из данных и шаблонов;
- реестр строится как проекция состояния документов и связанных сущностей;
- ручное редактирование DOCX/PDF не должно становиться основным способом изменения данных;
- повторная генерация артефакта должна быть предсказуемой и воспроизводимой.

## MVP focus

MVP ориентирован на российскую исполнительную документацию по направлениям:

- ОВиК;
- ВК;
- АОСР;
- акты испытаний;
- сертификаты и паспорта;
- исполнительные схемы;
- реестры;
- комплекты ИД.

## Non-goals

PTO ID System не должен превращаться в:

- ERP;
- BIM;
- CAD;
- Google Docs;
- generic document constructor;
- enterprise document management system;
- файловый менеджер.

## Ключевой UX

Система должна быть document-centric: инженер ПТО работает с документами, реестрами и комплектами, а сложность структурированных данных скрыта за понятным интерфейсом.

Ключевые ожидания UX:

- автосохранение;
- блокировки документов при совместной работе;
- генерация DOCX/PDF из данных;
- работа с реестрами как с навигацией и контролем полноты;
- сохранение связей между актами, сертификатами, схемами, работами и комплектами ИД.

## Текущее состояние

Статус: архитектурная инициализация.

Разрешено:

- уточнять доменную модель;
- фиксировать ADR;
- проектировать UX и потоки данных;
- описывать границы MVP;
- готовить спецификации будущих модулей.

Запрещено без отдельного решения:

- создавать backend/frontend код;
- выбирать фреймворки;
- добавлять package manager и зависимости;
- создавать Dockerfile, CI/CD или deployment-конфигурацию;
- проектировать multi-tenant, роли, ЭЦП, интеграции и импорт legacy DOCX как реализованный функционал.

# 05. Инструкции для Codex-агента

## Роль агента

Codex работает в этом репозитории как архитектурный и инженерный помощник проекта PTO ID System. На текущем этапе агент не должен начинать реализацию приложения без явного запроса и отдельного архитектурного решения.

## Главные правила

1. Писать документацию на русском языке.
2. Сохранять стиль технической архитектурной документации.
3. Не создавать backend/frontend код без явного разрешения.
4. Не создавать `package.json`, lock-файлы, Dockerfile, CI/CD, конфигурации сборки и зависимости на архитектурном этапе.
5. Не превращать проект в generic document constructor.
6. Не считать DOCX/PDF источником истины.
7. Не считать реестр главной таблицей данных.
8. Любые решения, влияющие на архитектуру хранения, генерации, прав, версий и интеграций, фиксировать через ADR.

## Source of truth

При любых изменениях документации или будущего кода агент должен защищать принцип:

**SOURCE OF TRUTH = STRUCTURED DATA**

DOCX, PDF, XLSX, реестры, архивы комплектов и печатные формы являются производными артефактами.

Если пользователь просит реализовать сценарий, где данные берутся из DOCX/PDF как основного источника, агент должен явно отметить архитектурный риск и предложить отдельное решение по импорту или миграции данных.

## Работа с typed documents

Агент должен различать generic document и typed document.

Typed document имеет:

- тип;
- обязательные поля;
- доменные связи;
- правила валидации;
- жизненный цикл;
- шаблон генерации;
- влияние на реестры и комплекты.

АОСР, акт испытаний, сертификат и исполнительная схема не должны моделироваться как одинаковые произвольные страницы с полями. У них разная семантика.

## Работа с реестрами

Реестр всегда рассматривать как projection:

- его строки строятся из документов и связей;
- его экспорт является артефактом;
- его редактирование должно изменять structured data;
- его нельзя использовать как единственный источник истины.

Если будущая задача просит сделать таблицу реестра основной моделью, агент должен предложить альтернативу: RegistryProjection поверх доменной модели.

## Запреты текущего этапа

До отдельного запроса и ADR нельзя:

- выбирать стек приложения;
- добавлять зависимости;
- создавать scaffold;
- проектировать deployment;
- добавлять CI;
- реализовывать авторизацию;
- реализовывать multi-tenant;
- реализовывать ЭЦП;
- делать импорт DOCX/PDF как источник истины;
- добавлять интеграции с BIM/CAD/ERP.

## Как вносить изменения

При изменении архитектурной документации:

- сначала определить, какой документ отвечает за тему;
- не дублировать одно и то же решение во многих местах без необходимости;
- если решение долгосрочное и влияет на архитектуру, добавить или обновить ADR;
- если вопрос остается нерешенным, добавить его в roadmap/open questions;
- не подменять открытый вопрос случайной реализацией.

## Коммиты

Коммиты должны быть небольшими и осмысленными. Для архитектурных изменений использовать сообщения, отражающие содержание, например:

- `Initialize architecture documentation`;
- `Document registry projection model`;
- `Add ADR for template versioning`.

## Тон документации

Документация должна быть конкретной и прикладной. Избегать маркетинговых формулировок, абстрактных лозунгов и преждевременного выбора технологий.

# AI and temporary infrastructure prep

Дата: 2026-07-01

## Временный сервер и база для тестирования

Решение пока не реализуем, но направление такое:

- использовать обычный Postgres и Prisma `DATABASE_URL`, без привязки доменной
  логики к конкретному облаку;
- API держать отдельно от провайдера БД, чтобы переезд означал смену переменных
  окружения и миграций, а не переписывание продукта;
- файлы/вложения хранить через абстракцию object storage; предпочтительно
  S3-compatible интерфейс, чтобы можно было перейти между Supabase Storage,
  Cloudflare R2, Yandex Object Storage, AWS S3 и т.п.;
- не использовать provider-specific SDK в доменном коде. Только адаптеры на
  инфраструктурном уровне.

Практичный тестовый вариант:

1. Backend/API: Railway, Render или Fly.io.
2. Database: managed Postgres — Supabase Postgres, Neon или Railway Postgres.
3. Frontend: текущий Vercel.

Наиболее безболезненная связка для быстрого теста: Railway для API +
managed Postgres либо Supabase/Neon как внешний Postgres. В любом случае
продукт должен знать только `DATABASE_URL`, `DIRECT_DATABASE_URL` при
необходимости миграций и переменные object storage.

## Заготовка для ИИ в ИДее

Цель: пользователь загружает рабочую документацию, договор, чертежи,
сертификаты и участников в раздел; ИИ помогает собрать ИД, находит нехватки и
готовит черновики актов, а пользователь проверяет и утверждает.

Важно: на первом этапе не нужно “обучать модель с нуля”. Нам нужна управляемая
AI-система:

- ingestion: загрузка и разбор проектной/рабочей документации, договоров,
  чертежей, сертификатов, исполнительных схем;
- normalized facts: извлечённые факты по объекту, разделу, работам, материалам,
  документам, участникам, основаниям полномочий, датам;
- retrieval: поиск по загруженным документам и библиотекам раздела;
- AOSR skill pack: правила заполнения АОСР, последовательность пунктов,
  требования к материалам/документам/приложениям/подписям, формат дат и
  номеров;
- validation checklist: нехватка сертификатов, чертежей, подписантов, периода
  работ, проектных ссылок, приложений;
- draft generation: создание черновиков актов только как предложений;
- human review: пользователь всегда проверяет и подтверждает акт перед
  скачиванием/включением в комплект.

## Что считать “обучением”

Для ИДеи правильнее начать не с fine-tuning, а с набора инженерных артефактов:

1. Reference fixtures: реальные акты, шаблоны, эталонные DOCX, плохие и хорошие
   примеры.
2. Prompt/skill instructions: как заполнять каждый тег и пункт АОСР.
3. Evals: тесты качества — наличие обязательных полей, отсутствие выдуманных
   документов, корректные ссылки на сертификаты/чертежи, формат дат/номеров,
   отсутствие лишнего текста.
4. Grounding: ИИ может ссылаться только на данные раздела, библиотеки и
   загруженные документы.
5. Audit trail: каждое предложение ИИ должно объяснять, из какого документа или
   библиотеки взят факт.

Fine-tuning можно рассматривать позже, когда накопятся размеченные пары:
`исходные документы + библиотеки -> правильный комплект актов`, и когда evals
покажут, что обычный retrieval+prompting уже упёрся в потолок.

## Запреты для первой AI-заготовки

- не давать ИИ выпускать юридически значимый документ без подтверждения
  пользователя;
- не позволять ИИ выдумывать сертификаты, чертежи, подписантов или даты;
- не смешивать данные разных разделов без явного выбора пользователя;
- не привязывать AI-логику к одному провайдеру моделей;
- не хранить загруженные документы без workspace/section ownership модели.
